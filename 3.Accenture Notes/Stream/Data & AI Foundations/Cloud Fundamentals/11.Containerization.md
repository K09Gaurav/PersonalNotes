# Introduction

Modern applications are expected to run consistently across multiple environments, such as:

- A developer's laptop
- Testing environments
- Staging servers
- Production servers
- Public cloud platforms

Traditionally, moving an application between these environments often caused issues because each environment had different operating systems, libraries, software versions, or configurations.

This led to the common problem:

> **"It works on my machine!"**

Containerization solves this problem by packaging everything an application needs into a single portable unit called a **Container**.

> [!IMPORTANT]
> **Containerization packages an application together with all of its dependencies so it can run consistently in any environment that supports containers.**

---

# What is Containerization?

## Definition

**Containerization** is a method of packaging an application together with:

- Application code
- Runtime environment
- Libraries
- Dependencies
- Configuration files

into a single isolated unit called a **Container**.

The container behaves exactly the same regardless of where it runs.

Whether the container is executed on:

- A developer's laptop
- A QA server
- A cloud virtual machine
- Kubernetes

the application behaves consistently.

---

# What is a Container?

## Definition

A **Container** is an isolated execution environment that contains everything required to run an application.

A container includes:

- Application Code
- Runtime
- Libraries
- Dependencies
- Configuration Files

Unlike a Virtual Machine, a container **does not include its own operating system**.

Instead, containers share the host operating system's kernel while remaining isolated from one another.

> [!IMPORTANT]
> A container is an **isolated process**, not a separate operating system.

---

# Components of a Container

Every container typically contains:

- Application source code
- Runtime environment
- Required libraries
- Utilities
- Configuration files

Together, these components ensure that the application behaves identically across environments.

---

# Operating System-Level Virtualization

## Definition

Containers use **Operating System-Level Virtualization**.

Instead of virtualizing the entire hardware like Virtual Machines, containers isolate applications while sharing the same operating system kernel.

This makes containers:

- Lightweight
- Fast
- Resource-efficient

---

# How Containers Work

Containers run on a **Container Runtime**.

The runtime:

- Creates containers
- Starts containers
- Stops containers
- Manages container resources
- Isolates applications

Examples include:

- Docker Engine
- containerd
- CRI-O

---

# Why Containers Are Lightweight

Unlike Virtual Machines:

- Containers **share the host OS kernel**.
- They do **not require a separate operating system** for every application.

This reduces:

- Memory usage
- CPU usage
- Disk usage
- Startup time

# Benefits of Containers

Containers provide numerous advantages over traditional deployments.

---

## 1. Portability

Containers run consistently on any platform supporting the same container runtime.

A container built on a developer's machine can be deployed directly to production without modification.

> [!TIP]
> **Build Once, Run Anywhere**

---

## 2. Efficiency

Containers consume significantly fewer resources than Virtual Machines.

Since they share the host operating system:

- Less memory is required.
- Lower CPU usage.
- Smaller storage footprint.

---

## 3. Speed

Containers start extremely quickly.

Typical startup times:

- Containers → Seconds
- Virtual Machines → Minutes

This makes containers ideal for cloud-native applications.

---

## 4. Consistency

Because all dependencies are packaged together, applications behave the same across all environments.

This eliminates environment-specific issues.

Common phrase:

> "It works on my machine."

Containers solve this problem.

---

## 5. Scalability

Containers are designed for cloud environments.

They can easily be:

- Replicated
- Started
- Stopped
- Distributed

Container orchestration platforms like **Kubernetes** can automatically scale containers according to demand.

---

# Common Container Runtime Engines

A **Container Runtime** is software responsible for running containers.

Several container runtimes exist.

---

## Docker

The most popular container platform.

Features:

- Container creation
- Image management
- Networking
- Storage
- Container lifecycle management

---

## containerd

A lightweight container runtime.

Designed with:

- Simplicity
- Robustness
- Portability

Used internally by Docker and Kubernetes.

---

## CRI-O

A lightweight runtime specifically designed for Kubernetes.

---

## OpenVZ

An open-source Linux container virtualization platform.

---

## Rkt (Rocket)

A container runtime developed for cloud-native production environments.

Although largely discontinued, it played an important role in container evolution.

---

## LXC / LXD

Linux Containers provide operating-system-level virtualization.

Often used for lightweight Linux environments.

---

# Benefits of Containers Over Virtual Machines

---

## 1. Smaller Size

Virtual Machines include an entire operating system.

Containers include only:

- Application
- Runtime
- Dependencies

Typical sizes:

- VM → Gigabytes (GB)
- Container → Megabytes (MB)

---

## 2. Faster Startup

Containers start in seconds.

Virtual Machines often require several minutes because an entire operating system must boot.

---

## 3. Better Composability

Containers are defined using source code (such as a **Dockerfile**).

This allows:

- Automated builds
- Version control
- Reproducible environments
- Infrastructure as Code (IaC)

Virtual Machines are typically maintained as disk images.

# Containers and Microservices

Containers are especially useful for **Microservices Architecture**.

---

## What is a Monolithic Application?

A **Monolith** is a single large application where all features are tightly connected.

Example:

```text
Application
├── Authentication
├── Orders
├── Payments
├── Inventory
├── Notifications
```

All components are deployed together.

---

## What are Microservices?

A **Microservices Architecture** breaks a large application into many small independent services.

Each service performs one specific task.

Example:

```text
Authentication Service

Order Service

Payment Service

Inventory Service

Notification Service
```

Each service:

- Runs independently.
- Can be updated independently.
- Can scale independently.

---

# Why Containers Fit Microservices

Each microservice can run inside its own container.

Advantages:

- Independent deployment
- Independent scaling
- Fault isolation
- Easier maintenance
- Faster development
