# Introduction

As applications grow, they must support **thousands or even millions of users** simultaneously. Running a few containers manually is manageable, but modern cloud applications often require **hundreds or thousands of containers** distributed across many servers.

Managing these containers manually would involve tasks such as:

- Deploying new containers
- Monitoring container health
- Restarting failed containers
- Scaling containers up or down
- Updating applications with new versions
- Managing networking between containers

Performing these tasks manually is impractical.

To automate these operations, organizations use a **Container Orchestration Platform**.

The industry-standard orchestration platform is **Kubernetes**.

> [!IMPORTANT]
> **Docker creates and runs containers.**
>
> **Kubernetes manages containers at scale.**

---

# What is Container Orchestration?

## Definition

**Container Orchestration** is the automated management of containerized applications.

It automates tasks such as:

- Deployment
- Scaling
- Scheduling
- Networking
- Monitoring
- Self-healing
- Updates
- Resource allocation

Instead of manually managing containers, an orchestration platform performs these tasks automatically.

---

# Why Do We Need Kubernetes?

Imagine an application running:

- 5 containers → Easy to manage manually.
- 500 containers → Difficult.
- 5,000 containers → Impossible manually.

Modern cloud applications must:

- Handle millions of users.
- Run across multiple servers.
- Recover from failures automatically.
- Scale according to traffic.

Kubernetes was created to solve these challenges.

---

# What is Kubernetes?

## Definition

**Kubernetes (K8s)** is an **open-source container orchestration platform** that automates the deployment, scaling, networking, and management of containerized applications.

It was originally developed by Google and is now maintained by the **Cloud Native Computing Foundation (CNCF).**

> [!NOTE]
> Kubernetes is commonly abbreviated as **K8s** because there are **8 letters** between **K** and **s**.

---

# Why Kubernetes Became the Industry Standard

Earlier container orchestration tools included:

- Docker Swarm
- Apache Mesos
- CoreOS Fleet

Although these platforms are still available, Kubernetes has become the dominant solution because of its:

- Portability
- Scalability
- Self-healing
- Extensibility
- Large community
- Vendor neutrality

Today, Kubernetes is used by most organizations running cloud-native applications.

Kubernetes became popular because it solves many challenges associated with running applications at scale.

# 2. Scalability

Modern applications rarely experience constant traffic.

Traffic may:

- Increase during business hours.
- Spike during festivals or sales.
- Decrease overnight.

Kubernetes automatically adjusts workloads according to demand.

---

## Horizontal Pod Autoscaler (HPA)

Kubernetes uses the **Horizontal Pod Autoscaler (HPA)** to automatically increase or decrease the number of application instances (**Pods**) based on metrics such as:

- CPU usage
- Memory usage
- Custom metrics

### Example

```text
Morning → 3 Pods

Festival Sale → 30 Pods

Night → 3 Pods
```

This provides automatic elasticity.

---

# 3. Resilience (Self-Healing)

## Definition

Failures are expected in distributed systems.

Instead of preventing every failure, Kubernetes focuses on **recovering automatically**.

This capability is known as **Self-Healing**.

---

## Kubernetes Self-Healing Features

### ReplicaSet

Maintains the desired number of application instances.

If one Pod fails:

- Kubernetes automatically creates another.

---

### Readiness Probe

Determines whether an application is ready to receive user traffic.

If not ready:

- Traffic is temporarily stopped.

---

### Liveness Probe

Checks whether an application is still functioning.

If the application becomes unresponsive:

- Kubernetes automatically restarts it.

> [!IMPORTANT]
> Kubernetes automatically detects failures and attempts to recover without manual intervention.

---

# 4. Service Discovery

## Definition

Applications running inside Kubernetes need to communicate with one another.

Instead of remembering IP addresses, Kubernetes provides **Service Discovery**.

Applications simply communicate using service names.

---

## Cluster DNS

Kubernetes provides an internal **DNS service** that automatically resolves service names.

Example:

Instead of:

```text
10.12.5.18
```

Applications can simply use:

```text
payment-service
```

---

## Load Balancing

If multiple replicas of an application exist:

```text
Payment Service

Pod 1
Pod 2
Pod 3
```

Kubernetes automatically distributes incoming traffic across all Pods.

Benefits:

- Prevents overload.
- Improves availability.
- Better performance.

---

# 5. Extensibility

Kubernetes follows the **Building Block Principle**.

It provides simple core resources that can be extended.

---

## Custom Resource Definitions (CRDs)

A **CRD (Custom Resource Definition)** allows developers to extend the Kubernetes API.

Organizations can create entirely new Kubernetes resource types.

This makes Kubernetes extremely flexible.

---

# 6. Operational Cost

Efficient resource usage reduces infrastructure costs.

Kubernetes continuously optimizes:

- CPU
- Memory
- Storage
- Network usage

---

## Intelligent Scheduling

The Kubernetes Scheduler places workloads on nodes with sufficient resources.

Instead of randomly assigning applications:

Kubernetes chooses the most appropriate node.

This improves infrastructure utilization.

---

## Cluster Autoscaler

If the cluster becomes too busy:

New worker nodes are automatically added.

If demand decreases:

Unused nodes are removed.

This reduces cloud costs.

## What is a Cluster?

A **Cluster** is a collection of physical or virtual servers (**Nodes**) working together to run containerized applications.

```text
Cluster
│
├── Node
├── Node
├── Node
└── Node
```

---

# What is a Node?

A **Node** is an individual physical or virtual machine inside a Kubernetes cluster.

There are two types of nodes:

- Control Plane Nodes (Master Nodes)
- Worker Nodes

---

# Control Plane
## Definition

The **Control Plane** manages the entire Kubernetes cluster.

It makes global decisions such as:

- Scheduling workloads
- Monitoring nodes
- Managing deployments
- Maintaining cluster state

Think of it as the **brain** of Kubernetes.

---

# Control Plane Components

![Pasted image 20260708172357](../../images/Pasted%20image%2020260708172357.png)

---

## 1. kube-apiserver

### Definition

The **API Server** is the central component of Kubernetes.

It exposes the Kubernetes API.

Every operation passes through the API Server.

Examples:

- Create Pods
- Delete Pods
- Deploy applications
- Scale workloads

> [!IMPORTANT]
> **kube-apiserver is the nucleus (heart) of the Kubernetes cluster.**

---

## 2. kube-scheduler

Responsible for deciding:

**Which worker node should run a new Pod?**

It considers:

- Available CPU
- Available Memory
- Resource requirements
- Scheduling policies

---

## 3. kube-controller-manager

Runs various controllers that continuously compare:

**Desired State**

vs

**Actual State**

If differences exist:

Kubernetes automatically corrects them.

Example:

Desired:

```text
5 Pods
```

Actual:

```text
4 Pods
```

Controller creates the missing Pod.

---

## 4. etcd

A distributed **Key-Value Database**.

Stores:

- Cluster configuration
- Resource definitions
- Secrets
- Metadata
- Application manifests

It acts as the permanent storage of Kubernetes.

---

# Data Plane (Worker Nodes)

## Definition

Worker Nodes execute application workloads.

Containers actually run here.

---

# Worker Node Components

![Pasted image 20260708172510](../../images/Pasted%20image%2020260708172510.png)

---

## kubelet

Runs on **every node**.

Responsibilities:

- Registers node with the API Server.
- Starts containers.
- Monitors Pods.
- Reports node health.

---

## kube-proxy

Responsible for networking.

Functions include:

- Routing traffic
- Load balancing
- Service connectivity
- Network accessibility

---

> [!NOTE]
> Both **kubelet** and **kube-proxy** are installed on **every node** (both Control Plane and Worker Nodes) to maintain communication and connectivity.

# Interview One-Liners

**Kubernetes**
> An open-source container orchestration platform that automates the deployment, scaling, and management of containerized applications.

**Container Orchestration**
> The automated management of container deployment, scaling, networking, monitoring, and recovery.

**Cluster**
> A collection of nodes that work together to run containerized workloads.

**Node**
> A physical or virtual machine that participates in a Kubernetes cluster.

**Control Plane**
> The management layer responsible for scheduling, monitoring, and controlling the Kubernetes cluster.

**Worker Node**
> A node responsible for running application workloads inside Pods.

**kube-apiserver**
> The central management component that exposes the Kubernetes API and handles all cluster operations.

**kube-scheduler**
> Assigns Pods to the most suitable worker node based on available resources.

**kube-controller-manager**
> Ensures the actual cluster state matches the desired state.

**etcd**
> A distributed key-value store that maintains the cluster's configuration and state.

**kubelet**
> The node agent that communicates with the API Server and manages containers on each node.

**kube-proxy**
> A network component that provides service networking and load balancing within the cluster.

**Horizontal Pod Autoscaler (HPA)**
> Automatically adjusts the number of Pod replicas based on workload metrics.

**ReplicaSet**
> Ensures the desired number of identical Pod replicas are always running.

**Custom Resource Definition (CRD)**
> A mechanism for extending the Kubernetes API with custom resource types.
