# Amazon DynamoDB

---

# Introduction

**Amazon DynamoDB** is a **fully managed, serverless NoSQL database service** provided by AWS. It is designed to deliver **high performance, low latency, and virtually unlimited scalability**, making it ideal for modern cloud-native applications.

Unlike traditional relational databases, DynamoDB does **not require a fixed schema**, allowing developers to store and retrieve data flexibly without worrying about changing table structures as applications evolve.

DynamoDB is built to support applications that handle **millions of requests per second** while maintaining **single-digit millisecond latency**.

> [!IMPORTANT]
> **Amazon DynamoDB is a Serverless NoSQL Database that automatically scales and requires no server management.**

---

# What is a NoSQL Database?

A **NoSQL (Not Only SQL)** database is designed to store data without requiring a predefined table structure (schema).

Unlike relational databases, where every row must follow the same column structure, NoSQL databases allow records to have different attributes.

Example:

### Traditional SQL Table

| EmployeeID | Name | Department |
|------------|------|------------|
| 101 | Alice | HR |
| 102 | Bob | IT |

Every row must contain the same columns.

---

### DynamoDB (Schema-less)

```json
{
  "EmployeeID": 101,
  "Name": "Alice",
  "Department": "HR"
}
```

```json
{
  "EmployeeID": 102,
  "Name": "Bob",
  "Department": "IT",
  "Skills": ["AWS", "Python", "Docker"]
}
```

Notice that the second record contains an additional field (**Skills**) without requiring any database schema changes.

> [!NOTE]
> In DynamoDB, items in the same table can contain different attributes.

# How DynamoDB Works

```text
Application
      │

DynamoDB Table
      │
      ▼

      │
      ▼
Attributes (Key-Value Pairs)
```

---

# Key Concepts

## Table

A **Table** is the primary container that stores related data.

Example:

```text
Users
Orders
Products
Employees
```

---

## Item

Each record in a DynamoDB table is called an **Item**.

In many NoSQL databases, an item is also referred to as a **Document**.

Example:

```json
{
    "CustomerID": 101,
    "Name": "John",
    "City": "Delhi"
}
```

---

## Attributes

Attributes are the individual pieces of information stored inside an item.

Example:

```json
{
    "Name": "John",
    "Age": 25,
    "Country": "India"
}
```

Here:

- Name
- Age
- Country

are attributes.

---

# Data Model

DynamoDB supports two primary NoSQL data models:

## Key-Value Store

Stores data using a unique key and its associated value.

Example:

```text
User123
      │
      ▼
{
   Name: "John",
   Age: 24
}
```

---

## Document Database

Stores structured data as JSON-like documents.

Example:

```json
{
    "OrderID": 501,
    "Customer": "John",
    "Products": [
        "Laptop",
        "Mouse"
    ]
}
```

---

# Primary Key

Every DynamoDB table requires a **Primary Key**.

The primary key uniquely identifies each item in the table.

DynamoDB commonly performs operations such as:

- GET
- PUT

using the Primary Key.

---

# Serverless Architecture

DynamoDB is completely **serverless**.

You do **not** need to:

- Provision servers
- Install database software
- Patch operating systems
- Upgrade database versions
- Manage infrastructure

AWS automatically manages everything.

---

# High Availability

DynamoDB automatically replicates data across:

```text
Three Availability Zones (AZs)
```

within the same AWS Region.

This provides:

- High availability
- Fault tolerance
- Improved durability

# Real-World Example

An online shopping application might use DynamoDB to store:

```json
{
  "CustomerID": "C101",
  "Name": "Alice",
  "CartItems": [
    "Laptop",
    "Keyboard"
  ],
  "Wishlist": [
    "Monitor"
  ]
}
```

If later the application introduces coupons, the item can simply become:

```json
{
  "CustomerID": "C101",
  "Name": "Alice",
  "CartItems": [
    "Laptop",
    "Keyboard"
  ],
  "Wishlist": [
    "Monitor"
  ],
  "Coupons": [
    "NEWUSER10"
  ]
}
```

No schema modification is required.

# Best Practices

- Use DynamoDB for applications requiring high scalability and low latency.
- Design tables around access patterns rather than complex relationships.
- Use primary keys efficiently for fast lookups.
- Choose DynamoDB over relational databases when data structures change frequently.
